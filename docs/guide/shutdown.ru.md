# Корректное завершение

Передайте пайплайну `ShutdownSignal`, и SIGINT (Ctrl+C) или SIGTERM аккуратно
остановят запуск:

```python
from sci_etl_core import AsyncETLPipeline, PipelineInterrupted
from sci_etl_core.signals import ShutdownSignal

pipeline = AsyncETLPipeline(
    extractor=extractor,
    relevance_filter=relevance_filter,
    entity_extractor=entity_extractor,
    exporter=exporter,
    state_manager=state_manager,
    shutdown=ShutdownSignal(),
)

try:
    count = await pipeline.run(query="all:galaxy", total_limit=500)
except PipelineInterrupted as stopped:
    print(f"Stopped after {stopped.partial_count} records; the next run picks up the rest")
```

Пайплайн устанавливает обработчики сигналов на время каждого `run()` и затем
возвращает прежние обработчики.

- **Первый сигнал:** новые записи не начинаются. Записи, уже находящиеся в
  обработке, завершаются, экспортёр выгружается, и записи, которые эта
  выгрузка сделала надёжно сохранёнными, помечаются как обработанные; записи,
  которые ещё не начались, остаются непомеченными до следующего запуска.
  Ожидающий запрос листинга или пауза между страницами отменяются немедленно.
  Сохранённый курсор не сдвигается дальше прерванной страницы. Экспортёр
  закрывается, состояние записывается на диск, и `run()` выбрасывает
  `PipelineInterrupted` с числом обработанных записей.
- **Второй сигнал:** восстанавливает прежний обработчик и немедленно завершает
  процесс.
- **Программная остановка:** `shutdown.request()` останавливает запуск так же,
  например из веб-обработчика или теста.

`PipelineInterrupted` — подкласс `PipelineAborted`, поэтому существующий
`except PipelineAborted` по-прежнему его перехватывает. Перехватывайте
`PipelineInterrupted` первым, если прерванный запуск должен завершаться иначе,
чем неудавшийся.

## Синхронный пайплайн {#the-synchronous-pipeline}

`ETLPipeline` принимает тот же аргумент `shutdown`. Его работа выполняется в
фоновом цикле событий, поэтому обработчики устанавливаются в потоке, который
вызывает `run()`, и передают запрос этому циклу. Вызывайте `run()` из главного
потока, поскольку сигналы получает только главный поток:

```python
from sci_etl_core import ETLPipeline
from sci_etl_core.signals import ShutdownSignal

with ETLPipeline(..., shutdown=ShutdownSignal()) as pipeline:
    pipeline.run(query="all:galaxy", total_limit=500)
```

## Сброс экспортёра и состояния {#flushing-the-exporter-and-state}

Каждый запуск заканчивается выгрузкой и закрытием экспортёра, а затем вызовом
`flush()` менеджера состояния, как бы он ни завершился: успешно, аварийно,
прерыванием или отменой. `AsyncCsvExporter` формирует свой CSV-файл при
закрытии, а `AsyncSqliteStateManager` фиксирует контрольную точку журнала
упреждающей записи в `flush()`. Если сам запуск завершился неудачей, сбой
выгрузки или закрытия записывается в журнал, а не выбрасывается, чтобы не
скрыть исходную ошибку.

## Собственные обработчики {#handlers-of-your-own}

`shutdown.guard()` устанавливает обработчики на время блока вашего собственного
кода. Защитные блоки вкладываются друг в друга, поэтому пайплайн, получивший
тот же сигнал внутри такого блока, оставляет ваши обработчики на месте, когда
его запуск заканчивается. Обработчики устанавливаются только из главного потока;
в других потоках `guard()` записывает сообщение в журнал и ничего не
устанавливает, а `request()` по-прежнему работает.
