# 存储的所有权

由谁关闭存储之所以重要，是因为以下三个事实：

- SQLite 存储上的 `aclose()` 不是最终的：之后的调用会重新打开连接。
- `async with pipeline` 每次退出代码块时都会关闭 `closeables` 中的每一项。
- 存储的锁属于第一个争用它的事件循环。从第二个循环使用同一个实例会失败，但只在两者同时
  使用时才会失败，因此安静的测试能通过，而繁忙的界面会出错。

所以，要为每个存储实例指定恰好**一个所有者**，即比它的所有使用者存活更久的作用域，并且
只让所有者调用 `aclose()`。每个实例只在**一个事件循环**中使用。其他一切都只是借用：
`AsyncHybridSearcher`、边来源和 `AsyncCompositeIngestor` 从不关闭存储。

| 部署方式 | SQLite 存储的所有者 | 流水线的 `closeables` |
|----------|---------------------|-----------------------|
| 流水线和界面在不同进程中 | 每个进程，各自负责它在共享文件上打开的实例 | 列出流水线自己的实例 |
| 在 `async with pipeline` 内摄取并查询的一次性脚本 | 流水线 | 列出这些存储；查询在代码块内运行 |
| 在单个事件循环上运行、会启动摄取运行的长期应用 | 应用程序，在关闭时关闭它们 | **不得**列出它们，否则每次运行结束都会关闭它们，下一次查询会重新打开一个无人拥有的连接 |
| 阻塞式 `ETLPipeline` 加上一个运行在自己循环上的应用 | 同一组文件上的两套实例：一套供流水线的后台循环使用，一套供应用程序的循环使用 | 列出流水线那一套 |

SQLite 的 WAL 模式允许一个进程读取的同时另一个进程写入。
