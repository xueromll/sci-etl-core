# Журналирование

Каждый модуль sci-etl-core пишет журнал через стандартный модуль `logging`,
в логгер, названный по имени модуля, например `sci_etl_core.pipeline_async` или
`sci_etl_core.extractors.arxiv_async`. Все они находятся под логгером
`sci_etl_core`. Библиотека не устанавливает обработчиков и не задаёт уровней,
поэтому ничего не выводится, пока приложение не настроит журналирование:

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
    handlers=[logging.FileHandler("pipeline.log", encoding="utf-8"), logging.StreamHandler()],
)
logging.getLogger("sci_etl_core.extractors").setLevel(logging.WARNING)
```

Уровни означают следующее:

| Уровень | Для чего используется |
|---------|-----------------------|
| `ERROR` | Сбой стока или хранилища, о котором сообщает запуск: не удался `flush` или `aclose` экспортёра, не удалось записать состояние на диск, не удалось закрыть ресурс, обработчик событий выбросил исключение |
| `WARNING` | То, что меняет результат запуска или его стоимость: запись не удалась или была пропущена, запись помещена в карантин, источник остановился на своём лимите результатов или отверг курсор, отказал бэкенд памяти, загрузка оказалась непригодной, повторная попытка, сигнал завершения |
| `INFO` | Рутинные заметки: сущность или утверждение отклонены валидацией, место, с которого возобновился запуск `newest_first` |

Сообщения сохраняют формулировки, которые ранние релизы передавали в
вызываемые объекты `logger=`, например
`Record processing failed: LLMError('...')`, поэтому написанные под них
фильтры и оповещения по-прежнему срабатывают.

Структурированным каналом остаются события прогресса из раздела
[Наблюдаемость](observability.md): считайте записи, страницы и исходы по
событиям, а журнал используйте, чтобы узнать причины.
