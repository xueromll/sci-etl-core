# 路线图

本路线图说明的是方向，而不是承诺。优先级取决于真实的使用场景，而且每一项都必须符合本库的
范围：输入科学论文，输出结构化、可检索的数据。不符合范围的事项会被拒绝，无论它在别处多么
有用。如果想参与某一项，请在其议题下留言或新建一个议题。标记为 **good first issue** 的事项
适合新手。

每个里程碑都列出了完成标准。只有当测试套件离线运行、行覆盖率为 100%，且每条标准都满足时，
该里程碑才会发布。

尚未完成：

- sci-etl-cli 0.4.0 和 udg-catalogue 改用已发布的 0.6.0，要求 `>=0.6.0,<0.7` 而不是开发
  版本，并且运行时没有 `DeprecationWarning`。
- 实际检查 OpenAlex 游标的有效期有多长。

PubMed 和 Semantic Scholar 保留按偏移量分页，并把各自的上限报告为截断：即使通过历史服务器，
E-utilities 最多也只提供 9,999 条结果；Semantic Scholar 的批量检索返回固定为 1,000 篇论文的
页面，无法遵循 `page_size`。

## 通往 1.0 之路 {#path-to-10}

每个公开契约在 1.0 之前计划内的最后一次破坏性变更都已完成。运行契约（提取器、状态、构造
函数）在 0.5.0 中发生了破坏性变更，数据契约（实体、导出器、日志、依赖）在 0.6.0 中发生了
破坏性变更；此后的每个版本都只做增量修改。每项破坏性变更都在 [MIGRATION.md](migration.md)
中有对应条目。

自 0.6.0 起，已弃用的名称在被移除之前至少还能在两个次版本中使用。只有当 sci-etl-cli 和
udg-catalogue 的测试套件在发布提交上通过时，才会打发布标签；发布工作流会运行两者，否则拒绝
发布。

## v0.7.0：增量功能与测试工具包 {#v070-additive-features-and-the-testing-kit}

不包含破坏性变更，也不引入新的弃用。

- **定向重新处理。** 一个可选的 `forget(record_ids)` 契约（两种内置状态管理器都会实现）可以
  在不丢弃全部状态的情况下重新提取记录。
- **级联相关性过滤器。** 一个组合过滤器先运行廉价的过滤器（例如
  `AsyncEmbeddingRelevanceFilter`），再运行 LLM 过滤器。
- **测试工具包。** `sci_etl_core.testing` 提供契约测试套件，第三方提取器、状态管理器、导出器
  和嵌入存储都可以运行。

## v1.0.0：稳定化 {#v100-stabilization}

1.0.0 保证三个层级：稳定名称遵循语义化版本，临时性名称可以在次版本中变更并在更新日志中记录，
私有名称可以随时变更。已知使用方导入的每个名称都是稳定的。当一个完整的次版本在没有破坏性
变更的情况下发布、公开接口快照和运行语义测试为每次变更把关，并且 0.6.0 和 0.7.0 写入的文件
都能在其中打开时，才会打候选发布标签。

## 以后 {#later}

这些事项要等到有使用方需要，或者有了测量结果之后才会进行。

- **知识综合（sci-etl-kg）。** 基于 0.6.0 的论断进行单位规范化、重复测量合并和合并效应量，
  放在一个基于 1.0.0 构建的独立包中。在满足下面的启动规则之前，这项工作留在 udg-catalogue
  中，因为只基于一份星表构建的层会把该星表的假设固化下来。核心库从不导入 sci-etl-kg，因此
  下面的任何结果都不会影响核心库的用户。
    - **第二份星表。** 1.0.0 发布之后，一旦有第二个构建星表的使用方需要单位规范化或合并，
      sci-etl-kg 0.1 就会以仅含这两项功能的形式启动，并基于稳定名称构建。
    - **没有第二份星表。** 如果到 2027 年 9 月仍没有第二份星表，sci-etl-kg 将移入“不计划”，
      直到出现第二份星表为止。
    - **闲置六个月。** 如果 sci-etl-kg 六个月没有发布，或者对它的维护拖慢了核心库的发布，
      它最后一个 0.x 版本将被冻结、标记为不再维护并归档。
    - **矛盾检测。** 矛盾检测和因果图不在任何发布计划之内；最多只停留在 notebook 和研究分支
      中。
- **可扩展的向量记忆。** 一个近似最近邻的 `AsyncEmbeddingStore`，用于精确扫描的 SQLite 存储
  无法交互式服务的语料库。待有语料库确定目标规模和延迟后启动。
- **候选池调优。** 在真实的记忆数据库（例如 udg-catalogue 的数据库）上测量排名靠前的文本块
  覆盖了多少条不同的记录，并根据测量结果设定 `chunk_pool_factor` 的默认值。
- **列式导出。** 用于后处理表格的 Parquet 输出端，放在一个可选 extra 之后。
- **单遍 PDF 解析。** `PdfPlumberParser.extract_text` 会把每个 PDF 打开两次，一次读取文本，
  一次读取表格。改为一遍读取两者。
- **引用边。** 一个用于共被引和文献耦合的边来源，基于 `AsyncOpenAlexExtractor` 保存在
  `metadata["references"]` 下的参考文献列表构建。
- **子串和 CJK 匹配。** 一个可选的三元组文本索引，会使索引大小大约翻倍。
- **发现界面。** 基于 `sci_etl_core.discovery` 读模型的交互式检索和图视图，作为 sci-etl-cli
  的子命令或独立应用在本仓库之外构建。

## 探索性事项 {#exploratory}

- **原生服务商客户端。** vLLM、llama.cpp 和 Ollama 等本地服务器已经可以通过 OpenAI 兼容客户端
  使用。只有对于没有 OpenAI 兼容端点的服务商，或者其结构化输出支持在该端点上缺失的服务商，
  才值得添加原生客户端。

## 不计划 {#not-planned}

这些事项经过考虑后已撤回；其中一些曾出现在早期的路线图中。

- **阻塞式编排契约。** 受支持的是异步 API。解析器和 pandas 处理器等阻塞式叶子组件保持阻塞；
  阻塞式的提取器、状态、导出器、LLM、相关性和实体契约、它们的适配器，以及其底层桥接的修复，
  都已撤回，改用对应的异步版本。

- **在库中按配置组装。** sci-etl-cli 已经能根据一个 YAML 文件构建完整的流水线。本库提供
  `from_config` 构建器；声明式组装留在 CLI 中，因此核心库不包含组件注册表。
- **流式流水线模式。** `on_event` 已经会在每条记录完成时报告。在页面落定之前就产出记录，会与
  “保存的偏移量只越过完全落定的页面”这一规则冲突。
- **处理器检查点。** 处理器链是对已导出表格的内存 pandas 变换，而该表格本身已经是持久化的
  检查点；重新运行处理链比持久化每一步更便宜。
- **分布式执行。** 状态管理器依赖本地文件锁和单一的 SQLite 写入者。把语料库拆分到多次相互
  独立、各自拥有状态的运行中，无需分布式运行时即可覆盖大型语料库。
- **重命名 `sci-etl-core` 或 `sci_etl_core`。** 发行包名称和导入名称保持不变。重命名需要一个
  过渡版本，并需要每个使用方进行迁移，而且对本库的功能毫无改变。
- **`sci-etl` 元包。** sci-etl-cli 已经带着所需的 extra 依赖核心库，因此元包只会让每次发布
  多出一次发布。
- **把 `sci-etl-cli` 重新发布为 `sci-etl`。** CLI 已经以 sci-etl-cli 的名称发布在 PyPI 上，并
  安装 `sci-etl` 命令。换一个新的发行包名称将是又一次重命名，并需要它自己的过渡版本。
