    Участие в разработке sci-etl-core¶

    Спасибо за интерес к улучшению sci-etl-core! Новые экстракторы, парсеры, экспортёры, бэкенды эмбеддингов и исправления документации искренне приветствуются — в том числе от тех, кто вносит вклад впервые. Это руководство поможет вам быстро начать работу.

    Участвуя, вы соглашаетесь соблюдать наш Кодекс поведения.

    Настройка среды разработки¶

    git clone https://github.com/xueromll/sci-etl-core.git
cd sci-etl-core

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -e ".[full,dev]"
    • Требуется Python 3.11+: кодовая база использует объединения X | Y и dataclass с slots=True, kw_only=True.
    • Зачем [full]: набор тестов задействует каждый встроенный компонент.
    • Для тестов не нужны: sentence-transformers и настоящий драйвер SQL — они подменяются моками или заглушками.

    Как устроена кодовая база — прочитайте сначала¶

    • Асинхронная реализация — единственная. Каждый компонент асинхронный (async). Не добавляйте синхронных двойников компонентов; генератора кода нет. Блокирующие реализации попадают в конвейер через адаптеры в _adapters.py.
    • Одна блокирующая точка входа. ETLPipeline (pipeline.py) запускает AsyncETLPipeline через _sync_bridge.run_sync. Новые блокирующие API сначала обсудите в задаче.
    • Не загружайте цикл событий. Выполняйте ресурсоёмкую или блокирующую работу через asyncio.to_thread. Парсеры, pandas, sqlite3 и файловый ввод-вывод следуют этому шаблону.
    • Внедряйте зависимости. Клиенты, парсеры, sleep и logger передаются аргументами конструктора, чтобы тесты могли их подменить. Принимайте logger: Callable[[str], None] | None и внедряемый sleep везде, где есть тайминги или повторы.
    • Никогда не глотайте отмену. Прежде чем перехватывать широкие исключения, перехватите и выбросите заново asyncio.CancelledError (см. llm/relevance_async.py).
    • Сообщайте о сбоях исключениями. Используйте иерархию из exceptions.py. Не возвращайте None или пустой результат при сбое транспорта — конвейер полагается на UpstreamError и MalformedResponseError, чтобы отличать сбои от конца данных.
    • Будьте безопасны при параллелизме. Конвейер вызывает фильтры релевантности, экстракторы сущностей, write экспортёра и mark_processed параллельно. Сериализуйте общие записи с помощью asyncio.Lock и пишите файлы через _atomic_io.atomic_write_text. Хорошие образцы — AsyncCsvExporter и AsyncFileStateManager.
    • Пишите журнал через логгер модуля. Каждый модуль журналирует через _logger = logging.getLogger(__name__): уровнем WARNING — всё, что меняет результат запуска или его стоимость, ERROR — сбой приёмника или хранилища, о котором сообщает запуск, INFO — рутинные заметки. Никогда не настраивайте обработчики или уровни; это задача приложения.
    • Импортируйте необязательные зависимости лениво. Каждый пакетный __init__.py сопоставляет публичные имена с их модулями в _EXPORTS и загружает их при первом обращении, поэтому импорт одного компонента никогда не требует необязательных зависимостей другого. Регистрируйте новые публичные имена там и в соответствующих импортах TYPE_CHECKING (тест проверяет, что они согласованы), а каждую новую стороннюю зависимость добавляйте в extra в pyproject.toml.
    • Никаких констант конкретной предметной области в ядре; оно должно оставаться независимым от области.

    Запуск тестов¶

    Набор тестов работает офлайн — не нужны ни сеть, ни живой LLM, ни сервис эмбеддингов.

    pytest                                                # всё офлайн
pytest tests/async                                    # асинхронные компоненты
pytest tests/contract                                 # соответствие ABC
pytest --cov=sci_etl_core --cov-report=term-missing   # отчёт о покрытии
    • Покрытие остаётся на 100 %. pytest --cov=sci_etl_core завершается ошибкой при покрытии ниже 100 % (настроено в pyproject.toml), поэтому новый и изменённый код требует покрывающих его тестов. Используйте # pragma: no cover только для строк, которые не могут выполниться на тестовой платформе, например для импортов, зависящих от ОС. CI также измеряет покрытие ветвей и показывает его в сводке задания; пока оно не является обязательным условием.
    • Асинхронные тесты используют явный маркер @pytest.mark.asyncio (автоматический режим не настроен), с AsyncMock или фикстурой mocker.
    • Никакой реальной сети и ожиданий отсрочки. Подменяйте HTTP-, LLM- и эмбеддинг-клиенты и внедряйте sleep=AsyncMock(), чтобы пропускать задержки отсрочки.
    • Контрактные тесты. Для каждой реализации публичного ABC есть случай в tests/contract/test_abc_conformance.py; добавляйте его для каждой новой реализации.
    • Тесты свойств. Помещайте инварианты — особенно те, которые должны разделять два бэкенда, например хранилища эмбеддингов в памяти и в SQLite, — в тесты Hypothesis в tests/test_properties.py.
    • Снимок публичного интерфейса. tests/api/public_surface.txt фиксирует сигнатуру каждого стабильного класса, поля, метода и функции, а tests/api/test_public_surface.py завершается ошибкой, когда код ей больше не соответствует. Если вы намеренно меняете публичный API, пересоздайте снимок, закоммитьте разницу и добавьте для неё запись в CHANGELOG.md:
    python tests/api/update_surface.py

    tests/api/surface.py перечисляет стабильные имена. Каждое имя, которое sci-etl-cli или udg-catalogue импортирует или наследует, должно быть среди них. tests/api/consumer_surface.txt перечисляет эти имена. Пересоздавайте его, когда меняется закреплённая версия у потребителя, читая каталог из его загруженной удалённой ветки, а не из локального клона, который может отставать:

    git -C ../udg-catalogue fetch origin
python tests/api/scan_consumers.py sci-etl-cli=../sci-etl-cli udg-catalogue=../udg-catalogue@origin/main
    - Живые тесты. tests/live выполняет по одному небольшому запросу к каждому встроенному источнику и проверяет возвращаемые записи, метаданные и полный текст. По умолчанию эти тесты исключены. Процесс Live запускает их каждую ночь и никогда не является обязательной проверкой. Запустите их локально командой pytest -m live tests/live. Ключи для более высокого лимита частоты необязательны и читаются из NCBI_API_KEY, SEMANTIC_SCHOLAR_API_KEY и OPENALEX_MAILTO. Без своего ключа источник, который продолжает отвечать 429, пропускается, а не считается проваленным. - Бенчмарк пропускной способности. python benchmarks/run_throughput.py прогоняет каждый встроенный экспортёр конвейера через AsyncETLPipeline на 1 000, 10 000 и 50 000 записях и записывает время в benchmarks/results/<version>.json. Экспортёр считается линейным, если его время на запись при наибольшем размере не более чем в 1,5 раза превышает время при наименьшем. --sizes, --repeats и --exporters сужают запуск. - Тесты потребителей. Процесс Downstream запускает наборы тестов sci-etl-cli и udg-catalogue на каждом push и pull request, устанавливая этот клон вместо выпуска, который закрепляет каждый проект, и завершается ошибкой при любом DeprecationWarning. Каждое задание устанавливает extras, указанные в собственном требовании проекта. Чтобы запустить набор тестов CLI локально:

    git clone https://github.com/xueromll/sci-etl-cli.git ../sci-etl-cli
pip install -e ".[config,async,arxiv,html,llm,pdf]"
pip install --no-deps -e ../sci-etl-cli
pip install click rich pytest pytest-asyncio pytest-mock pytest-cov
cd ../sci-etl-cli && python -m pytest -W error::DeprecationWarning

    И набор тестов udg-catalogue, который также устанавливает CPU-сборку PyTorch:

    git clone https://github.com/xueromll/udg-catalogue.git ../udg-catalogue
export PIP_EXTRA_INDEX_URL=https://download.pytorch.org/whl/cpu
pip install -e ".[config,async,arxiv,html,llm,pdf,processors,cluster,embeddings,embeddings-local,search]" \
    -r ../udg-catalogue/requirements/app.txt -r ../udg-catalogue/requirements/dev.txt
cd ../udg-catalogue && python -m pytest -W error::DeprecationWarning

    Стиль кода¶

    • Именование по PEP 8: функции и переменные в snake_case, классы в CapWords, константы в UPPER_CASE.
    • Аннотации типов в каждой публичной сигнатуре. Пакет поставляется с py.typed; поддерживайте их точность.
    • Небольшие функции с единственной ответственностью. Предпочитайте композицию и внедрение зависимостей ветвлению по жёстко заданной логике.
    • Docstrings для контрактов и намерений. Документируйте Raises: и неочевидные решения; не пишите комментарии, пересказывающие код.
    • Американский английский для идентификаторов и docstrings.

    ruff и mypy запускаются в CI на каждом push и pull request и настраиваются в pyproject.toml. ruff проверяет наборы правил ASYNC, UP, RUF и PT помимо правил pycodestyle, Pyflakes, isort и bugbear. mypy проверяет основные контракты (models, exceptions, observability, pipeline_async и каждый модуль async_base) с более строгими флагами: без нетипизированных определений, без голых обобщённых типов, без возврата Any и без неявных реэкспортов. Запустите оба, прежде чем открывать PR:

    pip install -e ".[full,dev,lint]"
ruff check .
mypy

    ruff check --fix . сортирует импорты и применяет другие безопасные исправления. Форматирование не навязывается, поэтому не включайте в свой PR несвязанное переформатирование. Записывайте изменения, заметные пользователям, в раздел невыпущенной версии в CHANGELOG.md.

    Документация¶

    Сайт документации собирается с помощью MkDocs и Material for MkDocs из mkdocs.yml и папки docs/ и публикуется на GitHub Pages.

    pip install -e ".[docs]"
git clone https://github.com/xueromll/sci-etl-cli.git ../sci-etl-cli
pip install --no-deps -e ../sci-etl-cli
mkdocs serve                                          # предпросмотр на http://127.0.0.1:8000
mkdocs build --strict                                 # проверка, которую выполняет CI
    • Где находятся страницы. Руководства — это файлы Markdown в docs/, перечисленные в nav файла mkdocs.yml. CHANGELOG.md, MIGRATION.md, ROADMAP.md, это руководство, SECURITY.md и CODE_OF_CONDUCT.md остаются в корне репозитория; страницы в docs/project/ отображают их, а ссылки между ними переписываются для сайта.
    • Переводы. Русская, испанская, упрощённая китайская и арабская версии страницы лежат рядом с ней как page.ru.md, page.es.md, page.zh.md и page.ar.md, а плагин mkdocs-static-i18n собирает каждый язык по собственному пути, например /ru/. Pull request, меняющий английскую страницу, обновляет и четыре её перевода. TRANSLATING.md называет владельца каждого языка и содержит глоссарий и правила, которым следует переведённая страница.
    • Раздел CLI берётся из папки docs/ и nav репозитория sci-etl-cli. Сборка ищет клон рядом с этим или по пути из SCI_ETL_CLI_DIR; без него она пропускает раздел, о чём --strict сообщает как об ошибке. Меняйте страницы CLI в том репозитории.
    • Справочник API. Страницы в docs/reference/ генерируются из docstrings. Новому публичному модулю нужна запись module.path на одной из них; tests/test_docs.py завершается ошибкой, пока её нет.
    • Примеры кода. tests/test_docs.py также проверяет, что каждый пример на Python в docs/ компилируется и что каждое имя, импортируемое им из sci_etl_core, существует, поэтому переименование публичного имени означает и обновление примеров.
    • Публикация. Процесс документации развёртывает master как версию dev, а каждый тег v* — как его минорную версию, например 0.3, с псевдонимом latest. Сборка по тегу использует страницы CLI из последнего выпуска sci-etl-cli или из его ветки по умолчанию, если в этом выпуске нет mkdocs.yml. Вручную ничего публиковать не нужно.

    Выпуск версий¶

    • Версии для разработки. Сразу после выпуска master переходит на следующую версию для разработки, например 0.7.0.dev0 после 0.6.0, чтобы сборка из master никогда не выдавала себя за выпуск.
    • Условие выпуска. Push тега v* запускает набор тестов CI и процесс Downstream на помеченном коммите. Дистрибутив собирается и публикуется, только когда оба проходят, поэтому выпуск, ломающий sci-etl-cli или udg-catalogue, никогда не публикуется. Тег должен совпадать с версией в pyproject.toml.
    • Устаревания. Начиная с 0.6.0 устаревшее имя продолжает работать как минимум два минорных выпуска, прежде чем его удаляют.
    • Перед установкой тега. Проставьте дату в разделе невыпущенной версии CHANGELOG.md, обновите поддерживаемые версии в SECURITY.md и заново запустите python benchmarks/run_throughput.py, чтобы в benchmarks/results/ появилась новая версия.
    • Закреплённые actions. Процессы закрепляют каждый action на SHA коммита, указывая тег в комментарии в конце строки, например # v5. Чтобы перейти на более новый выпуск, определите его SHA командой git ls-remote https://github.com/actions/checkout refs/tags/v5 и обновите закрепление и комментарий одновременно.

    Формат коммитов¶

    Используйте Conventional Commits:

    <type>(<scope>): <short summary>

    Распространённые типы: feat, fix, docs, test, refactor, perf, chore. Помечайте ломающие изменения знаком ! (например, refactor(core)!: ...).

    Примеры:

    feat(extractors): add PubMed async extractor
fix(exporters): serialize concurrent CSV upserts
docs(readme): document ETLPipeline event-loop behavior

    Пишите краткое описание в повелительном наклонении и короче ~72 символов. Ссылайтесь на задачи в теле сообщения (Closes #123).

    Процесс pull request¶

    1. Сначала откройте задачу для всего нетривиального, чтобы мы могли согласовать подход.
    2. Создайте ветку от master, например feat/pubmed-extractor.
    3. Пишите тесты вместе с изменением; сохраняйте покрытие на 100 %.
    4. Запустите набор тестов локально (а также линтер и проверку типов, если вы ими пользуетесь).
    5. Обновите документацию для изменений, заметных пользователям:
    6. страницы в docs/ — для использования; README.md оставляйте кратким обзором
    7. русский, испанский, китайский и арабский переводы каждой английской страницы, которую вы меняете, по правилам TRANSLATING.md; если вы не можете написать один из них, скажите об этом, и владелец языка добавит перевод до слияния
    8. MIGRATION.md — для ломающего изменения, в разделе выпуска, который его содержит
    9. docs/guide/migrating-a-pipeline.md — когда изменение влияет на перенос существующего конвейера на библиотеку
    10. ROADMAP.md — когда вы выпускаете пункт из списка
    11. описание pull request — для любого ломающего изменения, с тем, что нужно обновить пользователям
    12. Заполните шаблон pull request.
    13. Держите PR сфокусированными — одно логическое изменение на PR проще всего проверять.

    Сопровождающий быстро проведёт ревью. Ожидайте дружелюбного, конструктивного общения; запрошенные изменения касаются кода, а не вас.

    Добавление нового компонента¶

    Большинство вкладов подключается к существующему абстрактному базовому классу:

    Компонент Наследуйте Реализуйте Контракт
    Экстрактор AsyncExtractor async fetch_page(query, cursor, page_size) -> ListingPage, async fetch_full_text; cursor_for_offset, когда курсоры — десятичные смещения Возвращайте каждый элемент, который удаётся прочитать: конвейер сам пропускает обработанные идентификаторы. Учитывайте элементы без идентификатора в entries, возвращайте next_cursor=None на последней странице и truncated=True на странице, достигающей собственного лимита результатов источника. Выбрасывайте UpstreamError, когда источник недоступен после повторов, ExtractionError, когда он прямо отвергает запрос, MalformedResponseError для нечитаемой выдачи и StaleCursorError для курсора, который источник больше не принимает.
    Парсер Parser (при необходимости TableParser) extract_text(content: bytes) -> str Синхронный; вызывающий код запускает его в рабочем потоке. Выбрасывайте ParsingError для байтов, которые не удаётся прочитать.
    Клиент LLM AsyncLLMClient async complete_json(system_prompt, user_content, timeout); при необходимости complete_structured(..., schema, timeout) и invalidate(..., schema=None) Возвращайте разобранный объект JSON; выбрасывайте LLMError при сбое или когда тело ответа не является объектом JSON. Переопределяйте complete_structured, когда провайдер поддерживает вывод по JSON Schema; реализация по умолчанию вызывает complete_json.
    Кэш ответов LLM AsyncLLMResponseCache async get(key), async set(key, response), async clear() get возвращает None для отсутствующего ключа. Возвращайте копии, чтобы вызывающий код, изменяющий ответ, не мог изменить кэш. Выбрасывайте LLMCacheError при сбое хранилища; CachingLLMClient записывает его в журнал и вместо этого вызывает LLM. Добавьте aclose(), если удерживаете соединения.
    Фильтр релевантности AsyncRelevanceFilter async is_relevant(record) Выбрасывайте CancelledError заново.
    Экстрактор сущностей AsyncEntityExtractor[E] async extract(text) -> Sequence[E]; extract_record(record, text), когда нужна запись Конвейер вызывает extract_record, реализация которого по умолчанию вызывает extract. При сбое выбрасывайте исключение, а не возвращайте [], чтобы запись повторилась. Экстрактор, которому нужна запись, устанавливает requires_record = True; обёртка делегирует внутреннему extract_record.
    Экспортёр AsyncExporter[E] async write(record, entities); при необходимости open, flush, aclose и durable_writes Принимайте место назначения в конструкторе. write выполняется для каждой обработанной записи, включая запись без сущностей, возможно параллельно, и должен быть идемпотентным. При durable_writes = False flush должен делать надёжно сохранённой каждую предыдущую запись.
    Менеджер состояния AsyncStateManager load_processed_ids, mark_processed, load_metadata, save_metadata Безопасен при параллелизме. Переопределяйте record_failure и failure_counts для поддержки карантина; реализации по умолчанию ничего не отслеживают. Записывайте версию схемы и отказывайтесь работать с файлом более нового выпуска. Переопределите flush(), если используете буферизацию; добавьте aclose(), если удерживаете соединения.
    Эмбеддер AsyncEmbedder async embed(texts) -> list[list[float]] Один вектор на вход, в том же порядке; выбрасывайте EmbeddingError.
    Векторное хранилище AsyncEmbeddingStore add, delete_record, query, count Заменяйте фрагменты с тем же (record_id, chunk_index); delete_record удаляет все фрагменты записи. Переопределите replace_record (по умолчанию удаление, затем добавление), если ваш бэкенд умеет делать и то и другое атомарно. Никогда не возвращайте результаты с неконечными оценками. Ведите себя как InMemoryEmbeddingStore в отношении top_k, min_score и exclude_record_id. Сериализуйте использование общего соединения и выбрасывайте EmbeddingStoreError. Реализуйте iter_records (фрагменты в порядке chunk_index, записи в порядке record_id, без векторов), если текстовый индекс должен заполняться из вашего хранилища.
    Разбивщик TextChunker chunk(text) -> list[str] Упорядоченные фрагменты, покрывающие текст.
    Хранилище текстового поиска AsyncTextSearchStore свойство facet_keys, index, delete_record, search, filter_ids, get_documents, facet_counts, count Принимайте разобранные запросы, а не текст. Отвергайте запрос, который search не может ранжировать, с помощью require_rankable. Упорядочивайте равные оценки по record_id и применяйте фильтры до limit. Выбрасывайте ValueError до любого ввода-вывода для ключа фильтра или фасета вне facet_keys или для двух фильтров по одному ключу (validate_filters, validate_facet_keys). Принимайте MetadataFilter и RangeFilter, сравнивайте диапазоны через tag_in_range и заполняйте TextHit.snippets для каждого поля с подсвеченным совпадением. Переопределите range_counts (по умолчанию по одному filter_ids на диапазон), если умеете считать за одно чтение. Возвращайте те же результаты, что InMemoryTextSearchStore, и выбрасывайте SearchStoreError.
    Источник рёбер AsyncEdgeSource свойство kind, async neighbours(record_ids, limit) Сопоставляйте каждому запрошенному идентификатору, даже без соседей, не более limit пар (record_id, weight), лучшие первыми, где больший вес означает большую связанность. Никогда не закрывайте переданные вам хранилища.
    Процессор Processor process(frame) -> DataFrame Не изменяйте входной фрейм.
    Валидатор RecordValidator is_valid(record) -> bool; при необходимости validate(record) -> ValidationResult Работает с одним словарём сущности. Переопределите validate, чтобы называть поле и правило каждого отклонения; он должен отвергать ровно то же, что отвергает is_valid.
